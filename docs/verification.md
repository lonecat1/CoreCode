
## 一条命令

```bash
python tools/verify_all.py          # 全部，约 60 秒
python tools/verify_all.py --fast   # 跳过依赖 TS 仓库的三组对照
python tools/verify_all.py --full   # 再加变异检查（约 2 小时）
```

`--full` 期间**不能编辑 `src/`，也不能并行跑别的测试**——变异检查会反复把源码
改成各种错误版本。我在这上面踩过两次，症状都是「某个不相关模块的测试失败」，
很难往变异检查上联想。

### 被打断了怎么办

一轮全量约 3 小时。它被打断过**两次**（一次工具调用被 abort，一次会话跨夜
结束），第二次还留下了**已应用的变异**——`local_tool_shortcuts.py` 的护栏被
删掉了。现在两件事都有兜底：

| 情况 | 怎么办 |
|---|---|
| 有 `*.mutation-backup` 残留 | 直接再跑一次 `mutation_check.py`——`heal_leftovers()` 会先恢复 |
| 想接着上次跑 | 直接跑，它会读 `tests/.mutation_progress.json` 跳过已完成的 |
| 想完整重跑 | `python tools/mutation_check.py --reset` |

断点是**加速手段，不是正确性前提**：文件坏了、不存在、写不了，一律退化成
「从头跑」，绝不因此跳过未验证的条目。它也不进版本库——那是本机进度，提交
它会让人以为「这些条目已经验过了」。

## 每个检查能证明什么，以及**不能**证明什么

这一节是这份文档的核心。「能证明什么」写给使用者，「不能证明什么」写给
下一个想加检查的人——**不知道边界就会把通过当成正确**。

### 1. 单元测试（约 1600 项）

### 2. `check_imports.py` / `check_constants.py` / `check_orphans.py` / `check_duplicates.py`

| 能证明 | 不能证明 |
|---|---|
| 没有**结构性**死代码：导入不存在的名字、常量零引用、函数没人调、定义被遮蔽 | 被引用的东西**是否接在了正确的调用点上** |
| 注释里提到不算引用（「伪引用」） | 参数级死代码（`wrap_values=True` 无调用者时，这四个都看不见） |

> **「伪引用」是被真实骗过才加的检查**：常量只在 docstring 里被提到时，扫一眼
> 会觉得「有东西在用」，而实际没有任何代码读它。
>
> **参数级死代码是发现的盲区**：删掉 `/config-paths` 的折行渲染后，
> `render_key_value(wrap_values=True)` 再无调用者，四个检查器全绿。是变异检查
> 里那条「永远杀不死」的变异暴露了它。

### 3. `file_map.py` — 逐文件映射

| 能证明 | 不能证明 |
|---|---|
| 每个 TS 文件都有对应去向（映射 / TUI 排除 / 本实现独有，各有理由） | 映射到的那个文件**内容**是否真的等价 |
| 没有凭空多出来的 Python 模块 | 一个 TS 文件映射到两个 Python 文件时，两者是否都必要 |

> 它证明的是**覆盖度**，不是**正确性**。曾经有一句「77 个文件全部有对应实现」
> 长期没有依据——表并不存在；而按路径去搜，35 个文件根本不在表里。
> 现在是代码，跑一次就有结论。

### 4. `check_docs.py` — 文档里的数字

| 能证明 | 不能证明 |
|---|---|
| 文档写的数量与实测一致 | 文档的**结论**是否成立 |
| 数字不会无声漂移（生成块由脚本重写） | 手写数字的**句式**是否被完整覆盖 |

> 三个「常量数」曾在同一份文档里出现（267 / 269，实际 270）。**数字过期的
> 「可验证清单」比没有清单更糟**——它让人以为核过了。
>
> 句式覆盖不全的后果在本轮又出现一次：表格里写「596 个函数/类」，而检查器只认
> 「596 个**模块级**函数/类」。**句式追不上措辞变化**，所以现在易漂的数字
> 一律不写在散文里，只写在生成块中。

### 5. `e2e_compare.py` — 端到端对照

> **比文件强于比 stdout。** 这条是空断言逼出来的：第一版工具场景标成
> 「输出不同但文件一致」，跑完打印快照才发现 `a.txt` **一个字节都没变**——
> 管道 stdin 让权限提示遇到 EOF，两边都**拒绝**了。于是「文件一致」只证明
> 「两边都没做事」。
>
> **现状**：28 个场景，9 个逐字一致（5 个原有 + 4 条诊断命令）。

### 6. `compaction_compare.py` / `mcp_compare.py` — 纯函数与线协议

| 能证明 | 不能证明 |
|---|---|
| 同一批输入下，两边的**判定**（利用率/级别/是否剪/是否清）完全一致 | 真实长对话里的累积行为 |
| MCP：同一台服务器下，两边看到的工具表与调用结果一致 | 真实服务器（GitHub/filesystem 之类）的兼容性 |

> 压缩层第一版用例**全是 2 条消息**，13/13 全绿但 `snip` 永远 `too_few_messages`、
> `microcompact` 永远不动。**全绿但什么都没验证**。现在有一条元测试断言
> 「至少各有一个真正触发 / 明确拒绝的例子」。
>
> MCP 那组抓到一个**结构性 bug**：4 个通用工具被按服务器各注册一份，两台服务器
> 都发布资源时模型会收到同名工具，而 `find()` 只取第一个——第二台静默消失。
> **Python 侧的单元测试当时全绿**，因为它只测了一台服务器。

### 7. `mutation_check.py` — 测试有效性

| 能证明 | 不能证明 |
|---|---|
| 每条变异（330 条）都能让测试变红 | 测试**没覆盖到**的代码（变异只改已有片段） |
| 变异锚点无歧义（锚点唯一） | 测试断言的**语义**是否正确（一条永真断言也能「杀死」变异） |

> 它抓到过的东西里，最有价值的是**「杀不死的变异」**：
>
> - `CLEAR_MARKER = ""`：所有断言只检查「变了没变」（布尔），没检查清空后的**内容**
> - `wrap_values`：那条变异永远杀不死，因为整个参数已无调用者（死代码）
> - `file_map` 的存在性检查：测试自己遍历 `MAPPING`，**绕过了 `audit()`**
>
> 一条恒定存活的变异看起来像一个漏洞，实际往往是**检查项本身有问题**。

## 三条方法教训

### ① 用例必须**先被证伪**

写对照用例时，先确认它**能失败**，再让它通过。压缩层那两个「13/13 全绿」和
「工具文件一致」都是用例太弱——**全绿只是说明用例没碰到差异**。

具体做法：拿一条已知会出错的变化（改一个阈值、删一个字段）跑一遍，确认用例
报红。`mutation_check.py` 就是把这个动作自动化。

### ② 「有实现」不等于「已验证」

1. 端到端或纯函数**对照**过（有工具输出为证）
2. 逐字比对过（有 diff 为证）
3. 有测试 + 变异证明它不能坏

其余一律写「已实现，未验证」。

### ③ 检查器自己也要被检查

**一个永远返回「全部通过」的检查器，看起来和健康的检查器一模一样。**

`tests/test_checkers.py` 给检查器自己写了测试。它抓到过：
- `file_map.audit()` 的存在性检查被改成 `if False:` → 测试**照样全绿**
  （那条测试自己遍历 `MAPPING`，绕过了 `audit()`）
- `check_docs` 的三条判断逻辑内联在 `main()` 里 → 变异存活；抽成 `verify()`
  之后全杀

## 发现新缺口后的标准动作

第 3 步最容易被跳过。`utils/errors.ts` 那一次就是：查一个「不在映射表里」的
文件，顺带发现 `is_retryable_network_error` 把 `errno` 当字符串比较（永不命中）、
Windows 的 `errno.errorcode` 带 `WSA` 前缀（整张名字表落空）——三个问题同一个
成因链。
